# 실습 1. AI SaaS 약관에서 데이터 처리 조항 찾기

> 6장 [실습] 1번의 단계별 안내입니다. 실제로 쓰고 있는(또는 도입을 검토 중인) AI SaaS 하나의 기업용 계약 문서에서 데이터 처리 조항을 찾아 평가합니다. 소요 시간은 40~60분입니다.
> 개인·무료 요금제의 학습 설정과 보존 기간은 4장 실습 1에서 확인했습니다. 이 실습은 기업용 계약에서 그보다 더 들어가는 항목(데이터 처리 부속서, 하위 처리자, 보안 인증, 해결 시간, 사고 통지, 삭제 증명)에 집중합니다.

## 실습 시나리오

마케팅팀이 회의록을 자동으로 요약해 주는 AI SaaS를 도입하려고 합니다. 데모는 훌륭했고 가격도 적당합니다. 보안팀은 계약 전에 "우리 회의록이 어떻게 처리되는가"를 확인해 달라는 요청을 받았습니다.

## 1단계. 확인할 문서 모으기

AI SaaS는 보통 여러 문서에 정보를 나눠 둡니다. 아래 문서를 찾아 링크를 기록합니다.

| 문서 | 흔한 위치·이름 | 담긴 내용 |
|---|---|---|
| 이용약관 (Terms of Service) | 웹사이트 하단 | 서비스 이용 조건, 책임 제한 |
| 개인정보처리방침 (Privacy Policy) | 웹사이트 하단 | 수집 항목, 보존, 제3자 제공, 국외 이전 |
| 데이터 처리 부속서 (DPA) | 기업용 페이지, 법무·신뢰 센터 | 처리자로서의 의무, 하위 처리자, 사고 통지 |
| 보안·신뢰 센터 (Trust Center) | trust.회사명, security 페이지 | 보안 인증(ISO 27001, SOC 2), 암호화, 감사 보고서 |
| 하위 처리자 목록 (Sub-processors) | 신뢰 센터, DPA 부록 | 데이터를 함께 처리하는 다른 회사(클라우드, AI 모델 공급자) |
| AI 관련 정책 | AI 이용 정책, 모델 학습 FAQ | 입력 데이터의 학습 활용 여부 |

> 요금제(무료·개인·기업)에 따라 적용되는 문서가 다른 경우가 많습니다. 이 실습은 기업용 요금제의 문서를 기준으로 하고, 개인 요금제의 조건은 4장 실습 1의 결과와 비교만 합니다.

## 2단계. 키워드로 조항 찾기

각 문서에서 찾기(Ctrl+F)로 아래 키워드를 검색합니다.

| 확인 항목 | 검색 키워드 (한글 / 영문) |
|---|---|
| 학습 활용 | 학습, 개선, 훈련 / train, improve, model |
| 보존 기간 | 보존, 보관, 기간 / retain, retention, days |
| 삭제 | 삭제, 파기 / delete, deletion, erase |
| 처리 지역 | 국외, 이전, 지역, 서버 위치 / transfer, region, location |
| 하위 처리자 | 제3자, 위탁, 하위 / third party, sub-processor |
| 사고 통지 | 침해, 유출, 통지 / breach, incident, notify |
| 사람의 열람 | 검토, 열람, 직원 / human review, access by staff |

## 4단계. 도입 조건을 계약·설정·통제로 나누기

6-2에서 본 것처럼 계약은 받을 권리를 확보할 뿐, 사고를 막거나 나간 데이터를 되돌리지 못합니다. 그래서 찾은 결과를 세 가지로 나눠 도입 조건을 정합니다(표 6-6).

| 구분 | 내용 |
|---|---|
| 미명시 항목 | 4개 (해결 시간, SBOM·VEX 제공, 모델 변경 고지, 삭제 증명) |
| 계약에 넣을 것 | 미명시 4개 항목, 침해 통지 기한을 "72시간 이내"처럼 구체적으로, 하위 처리자 변경 사전 통지 |
| 관리 콘솔에서 설정·점검할 것 | 학습 제외 설정, 회의록 원문 보존 기간 단축, 처리 지역 지정(가능한 경우), 외부 공유와 연동 앱 제한. 서비스 업데이트로 기본값이 바뀌지 않았는지 분기마다 점검 |
| 우리 쪽에서 직접 할 통제 | 회사 SSO로만 로그인하고 개인 계정 사용은 차단(4-1), 회의록에 넣지 말아야 할 정보의 기준 안내, 공급자 로그와 별도로 우리 쪽 접속·사용 기록 보관 |
| 도입 불가 조건 | 기업 요금제에서도 학습 활용을 끌 수 없거나, 원문 보존 기간을 줄일 수 없는 경우 |

# 실습 2. Hybrid 경계에 가명처리 검문소 두기

> 6장 [실습] 2번의 단계별 안내입니다. 6-3 "Hybrid AI의 데이터 이동 통제"의 흐름(가명처리 → 외부 요약 → 사내 복원)을 작은 Python 프로그램으로 재현하고, 실제로 무엇이 경계를 넘는지 확인합니다. 소요 시간은 30분입니다.
> Python 3만 있으면 되고 외부 패키지는 쓰지 않습니다. 외부 AI 서비스는 받은 내용을 그대로 기록하는 흉내 서버(`fake_ai.py`)로 대신하므로 API Key가 필요 없습니다. 아래 결과는 2026년 10월 18일 WSL2의 Ubuntu 24.04, Python 3.12에서 실행한 것입니다.

## 실습 시나리오

온라인 쇼핑몰 "한빛몰"은 상담 기록을 외부 AI 서비스로 요약하려 합니다. 상담 원문은 사내에 두고, 이름과 전화번호를 가명으로 바꾼 내용만 밖으로 보낸 뒤, 돌아온 요약을 사내에서 실명과 다시 연결하는 구조입니다. 6-3에서 본 것처럼 핵심 질문은 하나입니다. **"실제로 무엇이 경계를 넘는가?"**

## 실습 파일

| 파일 | 역할 |
|---|---|
| `records.txt` | 상담 기록 3건. 이름, 전화번호와 함께 상담 내용 속에 계좌번호, 주소, 띄어 쓴 전화번호가 섞여 있음 |
| `customers.csv` | 사내 고객 DB를 흉내 낸 이름·전화번호 목록 |
| `fake_ai.py` | 외부 AI 서비스 흉내. 받은 내용을 `received.log`에 남기고 간단한 요약을 돌려줌 |
| `gateway.py` | 경계의 검문소. 가명처리 → 외부 호출 → 사내 복원 |

```bash
# ~/ai-cloud-security-labs가 없다면 SETUP.md 5단계를 먼저 합니다
cp -r ~/ai-cloud-security-labs/ch06-aiaas-vendor-evaluation/hybrid ~/hybrid-lab
cd ~/hybrid-lab
```

## 2단계. 검문소 없이 보내기

```bash
python3 gateway.py records.txt --direct

```

```text
[상담 1] 김민준 고객(010-2481-7730)이 주문한 운동화의 배송이 3일째 멈춰 있다고 문의함. …
[상담 2] 이서연 고객(010-5539-1204)이 사이즈 교환을 요청함. 환불 계좌로 국민은행 123456-01-789012를 불러 주며, …
[상담 3] 박지호 고객(010-7712-3368)이 서울시 마포구 월드컵로 15에 사는데 … 연락은 010 7712 3368로 달라고 함.
```

이름, 전화번호, 계좌번호, 주소가 모두 외부로 나갔습니다. 직원이 공개형 AI에 상담 기록을 붙여 넣을 때(4-1)와 같은 상태입니다.

## 3단계. 검문소를 거쳐 보내기

```bash
: > received.log            # 기록 비우기
python3 gateway.py records.txt --rules basic
```

```text
== 외부로 보낸 내용 ==
[상담 1] 고객01 고객(전화01)이 주문한 운동화의 배송이 3일째 멈춰 있다고 문의함. …
[상담 2] 고객02 고객(전화02)이 사이즈 교환을 요청함. 환불 계좌로 국민은행 123456-01-789012를 불러 주며, …
[상담 3] 고객03 고객(전화03)이 서울시 마포구 월드컵로 15에 사는데 … 연락은 010 7712 3368로 달라고 함.

== 사내에서 복원한 요약 ==
김민준 고객(010-2481-7730)이 주문한 운동화의 배송이 3일째 멈춰 있다고 …
```

고객 DB에 있는 이름과 전화번호는 가명(`고객01`, `전화01`)으로 바뀌어 나갔고, 돌아온 요약은 사내에서 실명으로 복원되었습니다. 가명과 실명의 대응표는 사내 검문소 안에만 있습니다.

그런데 외부로 보낸 내용을 다시 보면 **계좌번호, 주소, 띄어 쓴 전화번호**가 그대로 남아 있습니다. 고객이 상담 중에 직접 말한 정보라 고객 DB에 없고, 정해진 형식도 아니기 때문입니다. 6-3에서 "상담 내용 안에 고객이 직접 말한 계좌번호나 주소가 섞여 있어 가명처리를 피해 간다"고 한 바로 그 경우입니다.

## 4단계. 규칙을 강화해 다시 보내기

```bash
: > received.log
python3 gateway.py records.txt --rules strict
```

```text
== 외부로 보낸 내용 ==
[상담 2] 고객02 고객(전화02)이 사이즈 교환을 요청함. 환불 계좌로 국민은행 계좌X02를 불러 주며, …
[상담 3] 고객03 고객(전화03)이 서울시 마포구 월드컵로 15에 사는데 … 연락은 전화X01로 달라고 함.
```

`strict` 규칙은 숫자 모양으로 계좌번호와 띄어 쓴 전화번호를 찾아 가립니다. 그래도 **주소**는 여전히 나갑니다. 주소는 정해진 숫자 형식이 없어 간단한 규칙으로는 찾기 어렵습니다.

`[표 실습6-2]` 규칙에 따라 경계를 넘은 정보

| 정보 | 검문소 없음 | basic 규칙 | strict 규칙 |
|---|---|---|---|
| 고객 이름 | 나감 | 가명 | 가명 |
| 표준 형식 전화번호 | 나감 | 가명 | 가명 |
| 띄어 쓴 전화번호 | 나감 | 나감 | 가림 |
| 계좌번호 | 나감 | 나감 | 가림 |
| 주소 | 나감 | 나감 | **나감** |

## 5단계. 규칙만으로 부족할 때

규칙은 아는 형식만 찾습니다. 그래서 검문소에는 규칙 말고도 다음을 함께 둡니다.

- **보내는 데이터 자체를 줄입니다**: 요약에 주소가 꼭 필요한지부터 따집니다. 필요 없는 항목은 검문소 앞에서 아예 빼는 것이 가장 확실합니다(표 6-6 "보내는 데이터 최소화").
- **탐지 기술을 겹칩니다**: 실무 DLP와 AI Gateway의 민감정보 탐지는 규칙에 더해 주소·이름 같은 개체를 찾는 모델을 함께 씁니다. 그래도 완벽하지 않으므로, 확신이 낮은 문장은 보내지 않고 보류하는 정책을 둘 수 있습니다.
- **경계를 넘은 기록을 남깁니다**: 이 실습의 `received.log`처럼, 무엇이 나갔는지는 우리 쪽 검문소에서 기록해야 사고가 났을 때 영향 범위를 알 수 있습니다. 6-3에서 경고한 "디버깅 로그가 원문 그대로 외부 모니터링 서비스로 전송되는 경우"도 이 기록으로 찾아냅니다.

# 실습 3. AI Gateway로 공급자를 바꾸는 Exit 리허설

> 6장 [실습] 3번의 단계별 안내입니다. 6-4 "공급자 종속, 서비스 종료와 Exit Plan"의 추상화 계층과 대체 공급자 사전 검증을 직접 해 봅니다. 소요 시간은 40~60분입니다(모델 내려받기 포함).
> Docker와 Python 3가 필요합니다. Windows PC라면 [SETUP.md](../SETUP.md)의 1~5단계(WSL2·Docker 설치와 저장소 내려받기)를 먼저 마칩니다. 두 공급자는 로컬 모델 서버(Ollama)의 소형 모델 두 개로 대신하므로 API Key가 필요 없습니다. 아래 결과는 2026년 10월 18일 WSL2의 Ubuntu 24.04, Docker 29.1.3, Ollama 0.6.5에서 실행한 것입니다.

## 실습 시나리오

실습 2의 "한빛몰"은 상담 요약 기능을 외부 모델로 운영하고 있습니다. 어느 날 공급자가 지금 쓰는 모델을 6개월 뒤 폐기한다고 공지합니다. 업무 앱을 고치지 않고 다른 공급자로 옮길 수 있을까요? 옮긴다면 그 공급자는 지금만큼 잘하고, 지금만큼 안전할까요?

## 실습 파일

| 파일 | 역할 |
|---|---|
| `docker-compose.yml` | 두 공급자 역할을 할 로컬 모델 서버(Ollama, 버전 고정) |
| `routes.json` | Gateway의 경로 설정. 업무 이름(`summarizer`)을 어느 공급자의 어떤 모델로 보낼지(기본·대체) 정함 |
| `gateway.py` | 실습용 축소판 AI Gateway. 요청마다 `routes.json`을 읽고, 기본 공급자가 실패하면 대체 공급자로 전환하며, 모든 호출을 `gateway.log`에 남김 |
| `app.py` | 업무 앱. Gateway 주소와 업무 이름만 알고, 공급자와 모델 이름은 모름 |
| `eval_set.json`, `eval.py` | 평가셋 8건(요약 6건, 개인정보 2건)과 평가 스크립트 |

> `gateway.py`는 원리를 보기 위한 수십 줄짜리 축소판입니다. 운영에서는 LiteLLM 같은 AI Gateway가 같은 역할을 하며, 사용량 한도와 키 관리까지 맡습니다(10-3). 외부 패키지를 쓰지 않은 것은 실습 코드 전체를 직접 읽고 확인할 수 있게 하기 위해서입니다.

## 1단계. 두 후보를 기능 밖의 기준으로 먼저 보기

## 2단계. 실습 환경 띄우기

## 5단계. 모델 폐기 상황에서 자동 전환 확인하기

기본 공급자의 모델이 폐기된 상황을 흉내 내려고, `routes.json`의 `primary` 모델 이름을 없는 이름(`retired-model:1`)으로 바꾸고 앱을 실행합니다.

```bash
python3 app.py
tail -2 gateway.log
```

```text
[공급자 1 / qwen2.5:0.5b] 주문한 운동화의 배송이 3일째 멈춰서, 고객은 내일 출고를 요청합니다.
{"route": "summarizer", "role": "primary", "provider": "공급자 2", "model": "retired-model:1", "ok": false, "error": "HTTP Error 404: Not Found"}
{"route": "summarizer", "role": "fallback", "provider": "공급자 1", "model": "qwen2.5:0.5b", "ok": true, "sec": 0.87}
```

기본 공급자 호출은 404로 실패했지만, Gateway가 대체 공급자로 자동 전환해 업무는 멈추지 않았습니다(표 6-6 "장애 대응"의 대체 경로 자동 전환). 실패와 전환이 모두 `gateway.log`에 남아, 공급자 쪽 변경을 우리가 먼저 알아챌 수 있습니다.

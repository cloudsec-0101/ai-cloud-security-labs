# 실습 1. 가상 회사의 제로트러스트 4계층 커버리지 점검표 만들기

> 7장 [실습] 1번의 단계별 안내입니다. 코드는 쓰지 않습니다. 가상 기업 한빛제조의 시스템 현황 카드를 읽고, 시스템마다 그림 7-2의 네 계층을 거치는지 판정해 **"이 시스템은 네 계층 중 어디를 거치지 않는가?"**라는 질문에 답하는 점검표를 만듭니다. 소요 시간은 30분 안팎입니다.
> 혼자서도 끝까지 할 수 있도록, 판정에 필요한 사실은 모두 카드에 적어 두었습니다. 카드를 읽고 직접 판정한 뒤 정답표와 맞춰 봅니다.

## 실습 시나리오

1장 실습 1과 3장 실습 3에 나온 가상 기업 **한빛제조**(직원 300명)입니다. 1장 워크시트로 찾은 문제 일부를 고쳤고, 3장에서 정리한 상담 요약 챗봇을 운영하고 있으며, 최근 구매팀이 업무 Agent를 도입했습니다. 보안팀은 "제로트러스트를 도입했다"고 보고했지만, 시스템마다 실제로 네 계층을 거치는지는 아무도 정리해 본 적이 없습니다. 아래 내용은 설명을 위한 가상 예시입니다.

## 1단계. 시스템 현황 카드 읽기

**카드 A. 생산관리 시스템** — 생산·구매 담당자와 협력사 직원이 쓰는 핵심 업무시스템. 생산계획, 단가, 협력사 정보가 들어 있습니다.

- AWS의 가상 서버에서 웹으로 운영하며, 인터넷에 HTTPS로 공개되어 있습니다. 직원은 집 PC에서도, 협력사 직원은 협력사 PC에서도 접속합니다.
- 시스템 자체 ID와 비밀번호로 로그인하고, MFA는 없습니다. IT팀은 관리자 계정 2개를 여러 명이 함께 씁니다.
- 앞단에 접속 관문(ZTNA)이나 게이트웨이가 없습니다. 로그인하면 역할과 관계없이 모든 메뉴가 열립니다.
- 로그인 기록은 서버의 로그 파일에만 남고, 정기적으로 보는 사람이 없습니다.

**카드 B. Microsoft 365** — 전 직원의 메일, 문서, 메신저.

- 회사가 등록한 노트북과 휴대폰에서만 접속되도록 조건부 접근을 설정했습니다. 접속할 때마다 백신 동작과 OS 업데이트 상태를 확인합니다.
- 회사 통합 로그인(Entra ID)과 인증앱 MFA를 전 직원이 씁니다. 다만 전역 관리자 3명은 관리자 권한을 상시로 가지고 있습니다.
- 모든 로그인은 조건부 접근 정책을 거치고, 예전 방식의 기본 인증은 막았습니다. 문서 외부 공유는 협력사 도메인으로만 허용합니다.
- 로그인 기록과 파일 접근 같은 활동 기록이 보안관제(SIEM)로 모입니다. 평소와 다른 국가에서 로그인하는 등 위험 로그인이 탐지되면 추가 인증을 요구하거나 차단합니다.

**카드 C. AWS 관리 콘솔** — 생산관리 시스템의 서버와 데이터베이스를 관리하는 콘솔.

- 개발자와 IT인프라팀이 접속합니다. 어떤 기기로 접속하는지는 아무도 확인해 본 적이 없습니다.
- 올해 IAM Identity Center를 도입해 회사 통합 로그인과 MFA로 들어가게 했습니다. 그러나 예전에 만든 IAM 사용자 4명의 장기 액세스 키가 남아 있고, 개발자 2명은 `AdministratorAccess`를 상시로 가지고 있습니다.
- 통합 로그인으로 들어온 사용자는 직무별 권한 세트로 나눠 받습니다. 하지만 남아 있는 액세스 키만 있으면 통합 로그인을 거치지 않고 어디서나 API를 호출할 수 있습니다.
- 모든 API 호출이 CloudTrail로 기록되어 SIEM에 모입니다. 이상 징후가 나와도 담당자에게 메일만 가고, 접근이 자동으로 막히지는 않습니다.

**카드 D. 상담 요약 챗봇** — AI개발팀이 외부 LLM API와 상담 이력 RAG로 만들어 고객지원팀이 쓰는 서비스(3장 실습 3의 서비스 ②). 고객 개인정보가 들어 있는 상담 이력을 다룹니다.

- 고객지원팀 직원이 회사가 관리하는 브라우저에서만 쓰도록 했고, 기기 상태는 Microsoft 365와 같은 조건부 접근으로 확인합니다.
- 회사 통합 로그인과 MFA로 들어갑니다. 챗봇 관리자 권한은 필요할 때 신청해 4시간만 받습니다.
- 챗봇은 AI Gateway를 거쳐 승인된 모델만 호출합니다. 그런데 AI개발팀 개발자들은 개인 API Key로 같은 LLM을 직접 호출해, 상담 이력 데이터로 프롬프트를 시험하고 있습니다.
- 로그인 기록은 SIEM에 들어가고 위험 로그인 대응도 Microsoft 365와 같습니다. 그러나 프롬프트와 응답은 기록하지 않습니다.

**카드 E. 구매 자동화 Agent** — 협력사 견적 메일을 읽고 생산관리 시스템에 발주 초안을 올리는 Agent. 구매팀이 외부 개발자와 만들었습니다.

- 서버에서 24시간 도는 프로그램이라, 사람이 쓰는 기기가 없습니다.
- 메일과 생산관리 시스템에 접속할 때 팀이 함께 쓰는 장기 API Key와 생산관리 시스템 관리자 계정을 씁니다. 키는 1년째 바꾸지 않았습니다.
- MCP Gateway 없이 Tool에 바로 연결되고, 외부 인터넷 어디로든 나갈 수 있습니다.
- 실행 기록을 남기는지는, 개발을 맡았던 외부 개발자와 계약이 끝나 아무도 모릅니다.

판정이 갈리기 쉬운 칸은 다음과 같습니다.

- **B의 ②가 "충족"이 아닌 이유**: 통합 로그인과 MFA는 갖췄지만 전역 관리자 3명의 상시 권한이 남아 있습니다. 관리자 계정 하나가 털리면 전사 메일과 문서가 한꺼번에 넘어갑니다.
- **C의 ③이 "충족"이 아닌 이유**: 통합 로그인 사용자의 권한은 잘 나눴지만, 남아 있는 장기 액세스 키가 통합 로그인을 거치지 않는 뒷문입니다. ②의 장기 키 문제가 ③의 우회 경로로 다시 나타납니다.
- **D의 ③과 ④**: 챗봇 앱은 AI Gateway를 거치지만, 같은 데이터를 다루는 개발자의 개인 API Key 호출은 Gateway도, 기록도 거치지 않습니다. 사람의 로그인은 잘 지키는데 "AI에 무엇을 보냈는가"는 보이지 않습니다.
- **E의 ①이 "미충족"이 아닌 이유**: 사람이 쓰는 기기가 없으니 ① 사용자 계층의 기기 확인은 해당이 없습니다. 대신 Agent 자체의 신원(②)과 나가는 길(③)이 이 계층의 역할까지 맡아야 합니다(7-1의 Agent Identity, 7-4의 Egress 통제).
- **"모름"은 "미충족"보다 위험할 수 있습니다**: C의 ①과 E의 ④는 문제가 있는지조차 아무도 확인하지 않고 있다는 뜻입니다.

## 5단계. 빈칸에 우선순위 매기기

"미충족"과 "모름" 칸을 모아 다음 두 기준으로 정렬합니다.

- **데이터 등급**: 그 시스템이 다루는 데이터가 얼마나 중요한가? (7-2)
- **노출 정도**: 외부(인터넷, 협력사, 외부 메일)에서 닿을 수 있는가?

<details>
<summary>예시 답안 펼치기</summary>

1. **생산관리 시스템**: 네 칸 모두 미충족이고, 인터넷에 공개되어 협력사까지 접속하며, 단가와 협력사 정보를 다룹니다. 통합 로그인과 연동하고(SSO를 지원하지 않으면 앞단에 통합 로그인과 연동되는 접근 프록시나 ZTNA를 둡니다) MFA를 적용한 뒤, 공용 관리자 계정을 없애고 로그를 SIEM으로 보냅니다.
2. **구매 자동화 Agent**: 외부 견적 메일을 읽으므로 간접 Prompt Injection에 그대로 노출되어 있는데, 생산관리 시스템 관리자 계정을 쥐고 외부 어디로든 나갈 수 있습니다. Agent 전용 신원과 작업 단위 단기 자격증명으로 바꾸고, MCP Gateway와 Egress 허용 목록을 적용하고, 실행 기록부터 확인합니다(5-3, 5-4).
3. **AWS 관리 콘솔**: 남아 있는 장기 액세스 키가 통합 로그인을 우회하는 뒷문입니다. 키를 폐기하고, 상시 관리자 권한은 필요할 때만 부여하는 방식으로 바꾸고, 접속 기기를 확인해 "모름"을 없앱니다.

그다음 순서는 상담 요약 챗봇입니다. 개발자의 개인 API Key 직접 호출을 막고(AI Gateway 강제), 프롬프트와 응답을 마스킹해 SIEM으로 수집합니다.

## 6단계. (선택) 우리 회사 시스템 2개로 해 보기

우리 회사의 시스템 2개를 골라 같은 질문과 규칙으로 채워 봅니다. 사람이 매일 쓰는 시스템 하나와 AI 서비스 하나를 고르면 차이가 잘 보입니다. 이때는 카드가 없으므로, 칸마다 근거(사용 중인 솔루션, 설정 화면, 담당 팀)를 직접 확인해 적습니다. 근거가 없으면 "충족"으로 표시하지 않습니다.

# 실습 2. [토이 프로젝트] 내 PC에 미니 제로트러스트 랩 만들기

> 7장 [실습] 2번의 단계별 안내입니다. 그림 7-2의 네 계층을 오픈소스와 짧은 Python 코드로 연결해, 내 PC 한 대 안에 작은 "회사"를 만듭니다. 요청마다 판단하고(②), 집행하고(③), 탐지 결과가 다시 판단을 바꾸는(④→②) 흐름을 직접 확인합니다. 소요 시간은 1~2시간입니다.
> Docker가 필요합니다. Windows PC라면 [SETUP.md](../SETUP.md)의 1~5단계(WSL2·Docker 설치와 저장소 내려받기)를 먼저 진행합니다. 모든 명령은 WSL의 Ubuntu 터미널에서 실행합니다. 이 책의 실행 예시는 Ubuntu 24.04, Docker 29.1, Docker Compose 2.40에서 확인했습니다.

## 랩 구성

| 그림 7-2의 계층 | 랩의 구성요소 | 하는 일 |
|---|---|---|
| ① 사용자 | `try.sh`(요청 보내기), `devices.json`(등록 기기 목록) | 사용자·기기·접속 국가를 바꿔 가며 요청 |
| ② 인증·권한관리 | Keycloak 26(IdP), OPA 1.0(정책 엔진) | 로그인·토큰 발급, 요청마다 허용·추가 인증·차단 판단 |
| ③ 컨트롤 | `pep.py`(접근 게이트웨이) | 토큰 검증, OPA에 판단 요청, 결정 집행, 접근 로그 기록 |
| ④ 위험 탐지 | `detector.py` | 접근 로그를 3초마다 분석해 사용자별 위험 점수를 OPA에 반영 |
| 보호 대상 | `erp`, `aichat` | ERP(온프레미스 업무시스템)와 사내 AI 챗봇 역할의 작은 앱 |

```text
[try.sh] ──▶ [PEP :8000] ──판단 요청──▶ [OPA :8181] ◀──위험 점수── [detector]
   │             │                                                   ▲
   └─로그인─▶ [Keycloak :8080]   └──허용된 요청만──▶ [erp] [aichat]   │
                 │                     (내부망 back, 외부 포트 없음)    │
                 └──────────────── logs/access.jsonl ─────────────────┘
```

보호 대상 앱은 외부와 단절된 내부망(`back`)에만 붙어 있고 포트를 열지 않습니다. PEP를 거치지 않고는 닿을 길이 없습니다. 본문의 "우회 경로 없음" 요건을 구성으로 표현한 것입니다.

Keycloak은 뜨는 데 30초쯤 걸립니다. `curl -s localhost:8080/realms/zt`가 JSON을 돌려주면 준비된 것입니다.

> 실습 계정: `kim`(임직원, 역할 employee), `lee`(협력사 직원, 역할 partner). 비밀번호는 둘 다 `Passw0rd!`입니다.

> **로그인 방식에 대한 주의**
> `try.sh`는 명령줄에서 바로 시험하려고, 사용자 이름과 비밀번호를 IdP에 보내 곧바로 토큰을 받는 방식(Resource Owner Password Credentials, 흔히 Password Grant)을 씁니다. 이 방식은 앱이 사용자의 비밀번호를 직접 다루고 MFA를 거칠 수 없어서 OAuth 2.1에서 빠졌고, 실제 시스템에서는 쓰지 않습니다. 실무에서는 사용자가 브라우저로 IdP 로그인 화면에서 인증하는 방식(Authorization Code + PKCE)과 피싱 저항 MFA(7-1)를 거치게 하고, 서비스끼리의 호출에는 Client Credentials나 Workload Identity로 받은 단기 토큰을 씁니다. 이 랩의 계정과 Keycloak 설정(`keycloak/realm-zt.json`)도 실습용이므로 운영에 그대로 쓰지 않습니다.

> 🔎 (풀어 보기) **OAuth**는 비밀번호 대신 **토큰**으로 접근 권한을 주고받는 표준 약속입니다. 토큰을 받는 방법(Grant)이 여러 가지입니다.
> - **Password Grant**: 앱이 사용자의 아이디·비밀번호를 직접 받아 IdP에 내고 토큰을 받습니다. 명령줄에서 시험하기는 쉽지만, 앱이 비밀번호를 직접 다루고 MFA 화면을 띄울 수 없어 OAuth 2.1에서 빠졌습니다.
> - **Authorization Code + PKCE**: 사용자를 브라우저로 IdP 로그인 화면에 보내 거기서 로그인(MFA 포함)하게 하고, 앱은 그 결과로 받은 일회용 코드를 토큰으로 바꿉니다. 앱은 비밀번호를 보지 못하고, PKCE는 중간에서 코드를 가로채도 쓸 수 없게 하는 장치입니다.

## 2단계. 정책 엔진의 규칙 읽기

`policy/zt.rego`가 ② 정책 엔진의 판단 규칙입니다. 다음 중 하나라도 해당하면 차단합니다.

- 등록되지 않은 기기, 기기 소유자와 사용자 불일치, EDR이 동작하지 않는 기기
- 역할에 허용되지 않은 앱 (ERP는 임직원만, AI 챗봇은 임직원과 협력사)
- 보안 패치가 적용되지 않은 기기에서의 쓰기(POST) 요청
- 위험 점수 70 이상 (40~69는 차단 대신 추가 인증 요구)

## 5단계. 우회해 보기

PEP를 건너뛰고 앱에 직접 붙어 봅니다.

```bash
curl -s -m 3 http://localhost:9000 || echo "연결 실패(우회 불가)"
docker compose exec pep python -c "import httpx;print(httpx.get('http://erp:9000/home').json())"
```

첫 번째는 연결되지 않습니다. 앱이 포트를 열지 않았기 때문입니다. 두 번째는 PEP 컨테이너 안에서 내부망으로 직접 호출한 것이라 응답이 옵니다. 이 결과가 뜻하는 바를 생각해 보세요. 집행 지점 자체가 침해되면 뒤의 모든 것이 열립니다. 그래서 PEP는 가장 단단하게 지켜야 하는 구성요소이고, 앱도 `X-Verified-User` 헤더만 믿지 말고 PEP와의 통신을 상호 인증(mTLS)으로 확인해야 합니다.

> 🔎 (용어 풀이) **mTLS(상호 TLS)**: 보통의 HTTPS는 서버만 인증서를 보여 주고 클라이언트는 확인하지 않습니다. mTLS는 양쪽이 모두 인증서를 내보여 서로 확인합니다. 앱이 "이 요청은 진짜 PEP가 보낸 것인가"를 인증서로 확인하므로, 같은 내부망의 다른 컨테이너가 PEP인 척 헤더를 꾸며도 받아들이지 않습니다.

## 6단계. 위험 탐지가 정책을 바꾸는 순간

이제 kim이 몇 초 사이에 미국에서 접속한 것처럼 요청을 보냅니다. 비밀번호가 유출되어 다른 나라의 공격자가 로그인한 상황을 흉내 낸 것입니다.

```bash
./try.sh kim LAPTOP-KIM-01 erp US     # 미국에서 접속
sleep 5
docker compose logs detector | tail -3
curl -s localhost:8181/v1/data/risk   # 정책 엔진이 보고 있는 위험 점수
./try.sh kim LAPTOP-KIM-01 erp        # 다시 한국에서 접속
```

```text
detector-1  | [detector] kim: 위험 점수 0 → 15  ['최근 거부 1회']
detector-1  | [detector] lee: 위험 점수 0 → 30  ['최근 거부 2회']
detector-1  | [detector] kim: 위험 점수 15 → 65  ["5분 내 여러 국가 접속 ['KR', 'US']", '최근 거부 1회']
{"result":{"kim":65,"lee":30}}
{ "decision": "STEP_UP", "reasons": [ "위험 점수 65: 추가 인증 필요" ], "trace": "b2f62639" }
```

미국 접속 요청 자체는 허용되었습니다. 그 순간에는 판단할 근거가 없었기 때문입니다. 그러나 ④ 위험 탐지기가 로그에서 "5분 안에 두 나라"라는 신호를 찾아 위험 점수를 65로 올렸고, 정책 엔진은 같은 사용자의 다음 요청에 추가 인증을 요구했습니다. 여기서 몇 번 더 거부되면 점수가 70을 넘어 차단으로 바뀝니다. 사람이 개입하지 않고 탐지에서 정책 변경까지 몇 초 만에 이어졌습니다. 본문에서 말한 "탐지 결과가 보고서로 끝나지 않고 정책으로 되돌아가는 것"이 이것입니다.

위험 점수는 최근 5분의 로그만 보므로, 5분이 지나면 저절로 내려갑니다.

## 7단계. Trace ID로 한 요청 따라가기

모든 응답에는 `trace`가 붙어 있고, 같은 값이 `logs/access.jsonl`에 남습니다.

```bash

```

# 실습 3. RAG 검색에 문서 권한 유지하기

> 7장 [실습] 3번의 단계별 안내입니다. 7-2 "모습이 바뀌어도 등급은 유지되어야 한다"와 4-4의 "임베딩되는 순간 권한 정보가 사라진다"를 작은 RAG 검색으로 직접 확인합니다. 소요 시간은 20~30분입니다.
> Python 3만 있으면 되고 외부 패키지와 API Key가 필요 없습니다. 아래 결과는 2026년 10월 18일 WSL2의 Ubuntu 24.04, Python 3.12에서 실행한 것입니다.

## 실습 시나리오

회사가 사내 문서를 검색해 답하는 AI 챗봇을 열었습니다. 임직원과 상주 협력사 직원이 함께 씁니다. 원본 문서 저장소에서는 인사 문서는 인사팀만, 재무 문서는 재무팀만 열 수 있습니다. 그런데 문서를 RAG 색인으로 옮기면서 이 권한도 함께 옮겨졌을까요?

3장에서 본 것처럼 AI에게 "협력사 직원에게는 재무 문서를 보여주지 마"라고 지시하는 것은 통제가 아닙니다. 권한 검사는 AI 바깥, 문서가 프롬프트에 들어가기 전인 **검색 단계**에서 해야 합니다.

## 실습 흐름

```mermaid
flowchart LR
    DJ["docs.json<br/>원본 문서 5건과 열람 역할"]
    DJ -->|"index --no-acl"| I1["색인<br/>본문만, 권한 없음"]
    DJ -->|"index --acl"| I2["색인<br/>본문과 열람 역할"]
    Q["ask 역할 질문"] --> F{"색인에 열람 역할이 있고<br/>내 역할이 거기에 없는가"}
    I1 --> F
    I2 --> F
    F -->|예| X["제외"]
    F -->|아니오| SIM["질문과 겹치는 정도 계산<br/>상위 3건"]
    SIM --> PR["프롬프트에 넣을 문서"]
    PR -.-> LLM["LLM 답변"]
    FIX["원본 권한 수정"] -.-> DJ
    FIX -.->|"다시 index --acl 해야 반영"| I2
```

*[그림 실습7-2] 실습 3의 흐름: 원본 권한을 색인에 함께 옮기고, 검색 단계에서 역할로 거른 문서만 프롬프트에 넣는다*

1단계는 위쪽 경로(권한 없는 색인), 2단계는 아래쪽 경로(권한 포함 색인), 3단계는 점선으로 표시한 원본 권한 수정과 다시 색인하기를 따라갑니다. 권한 검사는 LLM에 닿기 전, 검색 단계의 마름모에서 끝납니다.

## 실습 파일

| 파일 | 역할 |
|---|---|
| `docs.json` | 원본 문서 5건과 문서마다 열람할 수 있는 역할(`allowed`) |
| `rag.py` | 색인 만들기(`index`)와 질문하기(`ask`). 질문과 가까운 문서를 찾아 "프롬프트에 넣을 문서"로 보여 줌 |

| 문서 | 열람할 수 있는 역할 |
|---|---|
| D1 사내 공지: 하반기 보안 교육 일정 | 임직원, 협력사, 인사팀, 재무팀 |
| D2 협력사 출입·시스템 이용 안내 | 임직원, 협력사 |
| D3 [인사] 2026년 임원 연봉 조정안 | 인사팀 |
| D4 [재무] 3분기 협력사 대금 지급 일정 | 재무팀 |
| D5 [구매] 협력사 단가 협상 내부 기준 | 임직원, **협력사** (구매팀이 실수로 협력사에 열어 둔 상태) |

> `rag.py`는 실제 RAG처럼 문서를 벡터로 바꾸지 않고, 글자 두 개씩 겹치는 정도로 질문과 가까운 문서를 찾습니다. 이 실습에서 보려는 것은 검색 기술이 아니라 **검색 결과가 누구의 권한으로 걸러지는가**입니다. Vector DB를 쓸 때도 원리는 같습니다.

> 🔎 (용어 풀이)
> - **RAG**: AI가 답하기 전에 사내 문서를 먼저 검색해, 찾은 문서를 질문과 함께 프롬프트에 넣어 주는 방식입니다. 모델이 모르는 사내 정보로 답하게 하려고 씁니다.
> - **색인(index)**: 검색을 빠르게 하려고 문서를 미리 정리해 둔 목록입니다. 책 뒤의 "찾아보기"와 같습니다. 원본 문서와 따로 저장되므로, 원본의 권한 정보를 함께 옮기지 않으면 색인에는 권한이 없습니다.
> - **벡터와 유사도**: 실제 RAG는 문장을 숫자 묶음(벡터)으로 바꾸고, 숫자가 비슷한 문서를 "질문과 가까운 문서"로 찾습니다. 이 실습은 이 과정을 단순하게 흉내 냈습니다.

## 3단계. 원본 권한을 고친 뒤 색인을 다시 만들기

구매팀이 실수를 알아채고 원본 문서(`docs.json`)에서 D5의 열람 권한을 임직원으로 줄였습니다. `docs.json`에서 D5의 `"allowed"`를 `["employee"]`로 고친 뒤, **색인은 그대로 둔 채** 다시 질문합니다.


```text

  → D1 사내 공지: 하반기 보안 교육 일정  (유사도 0.19)
```

원본은 고쳤지만 색인에는 예전 권한이 남아 있어 D5가 계속 보입니다. 색인을 다시 만들어야 사라집니다.

```text
  → D1 사내 공지: 하반기 보안 교육 일정  (유사도 0.19)
  → D2 협력사 출입·시스템 이용 안내  (유사도 0.19)
```

`[표 실습7-1]` 색인 방식에 따라 협력사 직원에게 보인 문서

| 단계 | D4 재무 대금 일정 | D5 구매 단가 기준 | 이유 |
|---|---|---|---|
| 권한 정보 없이 색인 | 보임 | 보임 | 색인으로 옮기며 원본 권한이 사라짐 |

| 원본만 고치고 색인은 그대로 | 안 보임 | 보임 | 색인에 예전 권한이 남음 |
| 원본을 고치고 다시 색인 | 안 보임 | 안 보임 | 원본과 색인의 권한이 일치 |

## 4단계. 실무에서는

- **권한은 원본에서 관리합니다**: 색인은 원본 권한을 따라갈 뿐입니다. 4-2의 "과다 공유 점검과 권한 정리"처럼 원본 저장소의 권한부터 정리해야 합니다.
- **권한 변경을 색인에 바로 반영합니다**: 원본 권한이 바뀌거나 문서가 삭제되면 Vector DB의 해당 조각도 바로 갱신·삭제되게 합니다(4-4 보안관리 방안 ③·⑤). 하루에 한 번 몰아서 다시 색인하면 그 사이에는 예전 권한이 살아 있습니다.
- **역할은 IdP에서 받습니다**: 이 실습에서는 역할을 명령줄로 넘겼지만, 실무에서는 사용자가 직접 정할 수 없도록 IdP가 발급한 토큰의 역할을 씁니다. 실습 2의 Keycloak 역할(employee, partner)이 바로 그 정보입니다.
- **문서 단위보다 더 잘게 나눌 수도 있습니다**: 한 문서 안에서도 일부만 민감하다면, 조각마다 등급을 붙이고 민감한 조각은 마스킹한 뒤 색인합니다(7-2).
